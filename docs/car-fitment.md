# Подбор по автомобилю: структура адресов и решения по SEO

Про то, как устроены страницы «товар под машину», почему их две ветки и
какие решения приняты сознательно. Формат поля — в `data/SCHEMA.md`,
общая картина — в `README.md`.

---

## Две ветки, два разных запроса

```
/podbor/bmw/3-seriya/e90/                    «что вообще есть на мою машину»
/catalog/stekla-far/bmw/3-seriya/e90/        «стёкла фар на мою машину»
```

Первая — узел на машину целиком: товары идут разделами, у каждого свой
заголовок и ссылка в соответствующую ветку каталога. Вторая — один раздел,
одна машина, ничего лишнего.

Это два разных поисковых интента, но только когда на машину есть товары
хотя бы двух разделов. Запрос «стекло фары бмв е90» уводит на вторую,
«что поставить в фары е90» — на первую.

Пока раздел на машину один, страницы совпадают товар в товар. На проде так
оказалось почти у всех машин: около 2850 из 4362 адресов sitemap были
парами дублей. Поэтому правило такое:

- **Раздел на узле подбора один** (марка, модель или поколение) —
  `/podbor/…` ставит canonical на ту же машину в ветке раздела и в
  sitemap не попадает. Ветка точнее под запрос: в её адресе, title и H1 есть
  название товара. Страница подбора остаётся доступной людям и передаёт
  ссылочный вес ветке.
- **Разделов два и больше** — у каждой страницы canonical на себя, обе в
  sitemap: это уже разные наборы товаров.
- Признак считает `singleBranchOf` в `src/lib/cars.ts` по дереву привязок.
  Canonical меняется только при появлении у машины второго раздела — это
  редкое событие, а не каждая правка товара.
- Заголовки, H1 и описания подбора собираются из реальных разделов машины
  (`categoryPhrase` в `src/lib/car-content.ts`): «Переходные рамки для
  Audi A4 B8», а не общее «Автосвет для Audi».

## Тексты страниц машин

Общий FAQ раздела на страницах веток больше не выводится: один и тот же
блок на сотнях адресов — дубль. Вместо него на каждой странице машины:

- «коротко» — сколько позиций, сколько в наличии, диапазон цен, бренды и
  ссылки на товары в наличии (`ListingFacts`);
- вопросы и ответы из данных именно этой машины (`carFaq`): что подходит,
  что в наличии, как проверить совместимость по поколению и годам.

FAQ раздела показывается только на странице самого раздела. Его можно
сгенерировать нейросетью в форме раздела в админке.

## Почему адрес вложен в раздел, а не наоборот

Рассматривались три схемы:

| Схема | Почему нет |
|---|---|
| `/catalog/stekla-far/auto/bmw/…` | лишний сегмент без ключевых слов, на уровень глубже от главной |
| `/podbor/bmw/3-seriya/e90/stekla-far/` | из раздела каталога ссылка уводит в чужую ветку, а «стёкла фар» оказываются в хвосте адреса |
| **`/catalog/stekla-far/bmw/3-seriya/e90/`** | выбрана: все слова запроса в пути, минимальная вложенность |

Цена выбора: второй сегмент адреса означает либо подраздел, либо марку.
Развели это запретом — у раздела с `carFitment` подразделов быть не может
(проверяет `saveCategory` в `src/lib/store.ts`), и наоборот. Роут один на
оба случая, `src/app/(shop)/catalog/[category]/[branch]/`: сначала
пробуется подраздел, затем марка. Двух страниц по одному адресу не
возникает.

Из-за того же запрета флаг доступен только разделам верхнего уровня. У
подраздела ветка начиналась бы с пятого сегмента
(`/catalog/aksessuary/maski/bmw/3-seriya/e90/`) — такие адреса поиск
обходит редко и ранжирует плохо. Если такой раздел всё-таки понадобится,
решение — поднять его на верхний уровень, а не удлинять адрес.

## Что удерживает индекс от разрастания

Матрица «разделы × марки × модели × поколения» потенциально огромна —
421 марка и 9871 поколение в справочнике. В индекс попадает только то, под
чем есть товар:

- дерево машин собирается из таблицы `product_cars` (`getCarTree`), а не из
  справочника, и дополнительно сужается по разделу;
- `generateStaticParams` всех четырёх уровней идёт по этому же дереву, так
  что несуществующая комбинация отдаёт 404, а не пустую страницу;
- товары разделов **без** `carFitment` в подбор не попадают вообще — иначе
  они стояли бы на страницах машин, а в форме товара поля для правки не
  было бы;
- `sitemap.xml` строится из того же дерева, поэтому пустых адресов в карте
  не бывает по построению.

## Внутренние ссылки

Страница, на которую ведёт только sitemap, обходится редко и ранжируется
плохо. Поэтому у каждой страницы ветки есть минимум два входа:

| Страница | Откуда на неё ссылаются |
|---|---|
| `/catalog/stekla-far/bmw/` | иконки марок на странице раздела; блок «что ещё подходит» у соседних разделов |
| `…/bmw/3-seriya/` | список моделей на странице марки; крошки |
| `…/bmw/3-seriya/e90/` | плитки поколений; страница поколения в `/podbor/`; тот же адрес в других разделах |
| `/podbor/bmw/3-seriya/e90/` | блок «весь автосвет для …» со всех страниц ветки; карточки товаров |

Блок «Что ещё подходит к BMW 3 серии E90» на страницах ветки — не
украшение: он связывает разделы между собой на одной и той же машине, и
«обманки на E90» получают ссылку с «стёкол фар на E90», а не только из
карты сайта.

## Разметка

На всех страницах обеих ветвей:

- `BreadcrumbList` — автоматически, из `Breadcrumbs`;
- `ItemList` с товарами страницы — `itemListJsonLd`;
- `Product` со ценами и наличием остаётся на странице товара, где ему и
  место: в списках он привёл бы к дублю предложений.

## Картиночный sitemap

Фотографии поколений перечислены у страниц **моделей** — там они и стоят,
плиткой выбора. У страницы поколения фотографии на странице нет (её убрали
из шаблона), и объявлять её в карте значило бы обещать поиску картинку,
которой на странице не найти.

## Что проверить после правок

```
npm run check          типы и линт
npm run build          все четыре уровня попадают в вывод сборки
npm run verify         метатеги, разметка, sitemap (нужен запущенный сайт)
```

Вручную стоит смотреть три вещи: 404 на несуществующей комбинации,
canonical подбора на ветку, когда раздел на машине один, и отсутствие
адресов без товаров в `sitemap.xml`. Вторую `npm run verify` проверяет сам
(«подбор и ветка раздела не дублируют друг друга»).
