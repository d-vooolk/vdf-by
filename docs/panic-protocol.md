# Протокол AID (тревожная кнопка)

«Настройки → Протокол AID» в админке. Видно администратору. Порядок как в
CRM: три подтверждения (кнопка каждый раз в другом месте), затем PIN.

**Неверный PIN.** Окно просто закрывается. После 3 неверных попыток кнопка не
срабатывает час, даже с верным PIN (счётчик в памяти процесса,
`src/lib/panic-guard.ts`).

**Верный PIN.** Происходит следующее (`src/lib/panic.ts`):

1. Снимок всей базы шифруется открытым ключом владельца в
   `var/panic/<дата>/database.db.gz.enc`. Если зашифровать не удалось —
   **ничего не удаляется**.
2. Из базы удаляются покупатели и их кабинеты, заказы, заявки на установку,
   SMS-журнал, бухгалтерия (списания, оплаты и отмены из CRM, очередь CRM),
   все сессии. У товаров и типов рамок стираются себестоимость и закупочная
   цена в долларах (`costPrice`, `costSource`). Каталог, настройки и входы в
   админку остаются.
3. `VACUUM` и checkpoint WAL — удалённые строки физически уходят с диска.
4. Удаляются локальные копии (`var/backups`, разовые `shop.before-*.db`).
5. Пишется файл-флаг `var/panic-remote-wipe`; cron на хосте
   (`deploy/panic-remote-wipe.sh`, каждую минуту) удаляет копии базы в Google
   Drive (`gdrive:vdf-backups/shop-*.db.gz`) насовсем, мимо корзины.
6. Протокол передаётся в CRM (`CRM_URL/api/integrations/panic/`, общий ключ +
   тот же PIN) — чтобы оба сервиса сработали от одного нажатия.

Нажатие в CRM точно так же дёргает VDF
(`VDF_URL/api/integrations/panic/`). Приём защищён общим ключом интеграции
(`CRM_INTEGRATION_KEY` здесь = `VDF_INTEGRATION_KEY` в CRM) и тем же PIN.

## Настройка

Ключи общие с CRM — один ключ восстановления на оба сервиса. Создаются один
раз в проекте prime-crm (`server/`): `npm run panic:keygen` (открытый ключ и
приватный — приватный на бумагу, в два места) и `npm run panic:pin` (PIN).

В `.env` магазина (`/var/www/vdf.by/.env`):

```
PANIC_PUBLIC_KEY=…   # тот же, что в .env CRM
PANIC_PIN_HASH=…     # тот же, что в .env CRM
```

`CRM_URL` и `CRM_INTEGRATION_KEY` уже заданы для синхронизации заказов — по
ним же передаётся протокол в CRM.

## После срабатывания

Архив лежит только на сервере, в `var/panic`. Без приватного ключа он
бесполезен, хранить можно где угодно:

```
scp -r root@93.125.12.160:/var/www/vdf.by/var/panic .
```

## Восстановление

Расшифровка — тем же инструментом, что у CRM (формат архива одинаковый):

```
cd prime-crm/server
npm run panic:decrypt -- <папка с архивом VDF>
```

Рядом с `database.db.gz.enc` появится `database.db.gz`. Дальше:

```
gunzip database.db.gz                      # → database.db
docker stop vdf
cp database.db /var/www/vdf.by/var/shop.db
rm -f /var/www/vdf.by/var/shop.db-wal /var/www/vdf.by/var/shop.db-shm
docker start vdf
```

Расшифрованные файлы — это открытые данные, после восстановления их нужно
удалить.

## Ограничения

Те же, что у CRM: кнопка не спасает от взлома с root-доступом (данные можно
забрать до нажатия), следы удалённых файлов какое-то время остаются на диске
VPS, логи запросов не очищаются (данных покупателей в них нет).
